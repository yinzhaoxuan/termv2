# DS-17 会话与应用两级内存账本（E3）

日期：2026-11-05
基线：main `e9f50e3`
出处：`REVIEW.md` GAP-09（「设计中的统一账本（每 Session 128 MiB、整个应用 512 MiB）及受控拒绝……按真实存活对象记账……验证没有虚扣、无限增长或悬空引用」）、§8 E3；`docs/TODO.md` §2.2。

凡写「决定」的地方，是本文替原设计补的选择。

## 0. 现状（2026-11-05 核实）

每个会话的主要内存都已有**局部**上限，但没有任何地方汇总：

| 消耗 | 位置 | 现有上限 |
|---|---|---|
| 屏幕网格（主屏 + 备用屏） | `Screen` / `Row::mem_bytes` | 列 × 行，很小 |
| 回滚历史 | `Scrollback::bytes_` | `memory_limit_bytes`（默认 64 MiB，DS-9 的 Profile 可配 8–1024 MiB）与行数，先到先淘汰 |
| 字素池（当前 store） | `PoolStore::bytes_` | 预算 `max(1 MiB, 历史上限 / 8)`，超 75% 压缩 |
| 被快照持有的**旧**字素池 | 快照的 `PoolRef` | **无**：压缩后旧 store 由快照持有，直到快照释放 |
| 核心事件队列、解析器缓冲 | `core.cpp` / `vt_parser` | 事件 1024 个；OSC 负载 1 MiB |
| 搜索结果 | `search.cpp` | 10 万条 |
| 渲染器持有的当前快照 | 后端 / 渲染器 | 一份 |
| 旧 attempt 归档文本 | `Win32PaneBackend::prevAttemptText_` | ≤ 8 MiB |
| 传输队列 | `io_queues.h` | 输出 4 MiB、用户输入 4 MiB、应答 64 KiB |

所以单个会话在默认设置下已低于 128 MiB。缺的是：① 量不出来；② 多个会话加起来没有应用级上限，开到第 N 个窗格也不会拒绝；③ 快照持有的旧字素池不在任何预算里；④ Profile 把历史上限设到 1024 MiB 时，单会话可以超过 128 MiB。

## 1. 目标与边界

做：

1. **按真实对象计量（拉取式）**：需要时从核心与后端现有对象算出当前占用，不做「申请 / 归还」式记账。没有预扣，也就不会「虚扣」或漏还。
2. **会话上限 128 MiB**：超出时调低该会话的历史内存上限，立即淘汰最旧的历史。
3. **应用上限 512 MiB**：所有会话合计超出时，从历史最大的会话开始调低历史上限，直到回到上限以内。
4. **受控拒绝**：新建窗格（新标签、分屏、恢复布局后点「连接」）前检查应用余量，不足就拒绝并说明原因；已有会话不受影响。
5. 诊断包里给出合计与每个会话的占用。

不做：

- 不把传输队列计入（由 `io_queues.h` 固定上限约束，每会话合计不超过约 8.1 MiB；计量它要改全部传输实现，本文不做）。账本说明里写明这一点。
- 不计显存、DWrite 缓存、进程 Private Bytes（GAP-09 要求「分开统计」，以后在诊断包里另列）。
- 内存回落后不自动把调低的历史上限调回去（决定：调低是粘性的，直到重连或新建窗格；避免来回抖动）。

## 2. 核心 API（`itcore.h`，按 ADR-005 均为兼容新增）

```c
typedef struct {
    uint32_t struct_size;          /* 调用方填 sizeof */
    uint64_t grid_bytes;           /* 主屏 + 备用屏 */
    uint64_t scrollback_bytes;     /* 回滚历史 */
    uint64_t pool_bytes;           /* 当前字素池 store */
    uint64_t pool_epoch;           /* 当前 store 的 epoch，与 itcore_snapshot_epoch 比较 */
    uint64_t queue_bytes;          /* 待取事件负载 + 解析器未完成的字符串缓冲 */
    uint64_t search_bytes;         /* 活动搜索的结果与状态（无搜索为 0） */
    uint64_t total_bytes;          /* 以上之和（不含 epoch） */
    uint64_t history_limit_bytes;  /* 当前生效的历史内存上限 */
} itcore_memory_usage;
/* 线程同 itcore_feed。只读，不分配。成功 0；参数无效 -1。 */
int itcore_memory_usage_get(const itcore_core *c, itcore_memory_usage *out);

/* 快照自身的行数据字节数，以及它持有的字素池 store 的字节数。线程：任意（快照可跨线程读）。 */
uint64_t itcore_snapshot_row_bytes(const itcore_snapshot *s);
uint64_t itcore_snapshot_pool_bytes(const itcore_snapshot *s);

/* 运行时调整历史上限：lines 为 0 保持不变；bytes 为 0 保持不变。
   立即按新上限淘汰最旧的历史；字素池预算随之改为 max(1 MiB, bytes / 8)。
   不影响已取出的快照。线程同 itcore_feed。成功 0。 */
int itcore_set_history_limits(itcore_core *c, uint32_t lines, uint64_t bytes);
```

- 计量都是对现有字段求和（`Row::mem_bytes`、`Scrollback::bytes()`、`PoolStore::bytes()`、事件 `data.size()` 加固定开销、解析器缓冲 `size()`），复杂度 O(屏幕行数 + 待取事件数)。
- `ABI-02` 断言表要加上新结构体（兼容新增，版本仍为 0）。

## 3. 会话占用（`app/pane_backend/pane_logic.h`，可移植）

```cpp
struct SessionMemoryInputs {
  itcore_memory_usage core;      // core 不存在时全 0
  uint64_t snapshotRowBytes = 0;
  uint64_t snapshotPoolBytes = 0;
  uint64_t snapshotEpoch = 0;
  bool hasSnapshot = false;
  uint64_t archiveBytes = 0;     // 旧 attempt 归档文本
};
// 快照 epoch 与 core.pool_epoch 相同：池与核心共享，不重复计；不同：旧 store 只被快照持有，计入。
uint64_t sessionMemoryTotal(const SessionMemoryInputs&);
```

`uishell::PaneBackend` 新增（默认实现返回全 0 / 空操作，桩与测试替身不必改）：

```cpp
struct MemoryUsage { std::uint64_t total = 0, history = 0, historyLimit = 0; };
virtual MemoryUsage memoryUsage() const;                 // UI 线程
virtual void setHistoryMemoryLimit(std::uint64_t bytes);  // UI 线程；对当前核心立即生效，重连沿用
```

`Win32PaneBackend`：`memoryUsage` 用 `itcore_memory_usage_get`、渲染器当前快照的两个 `itcore_snapshot_*_bytes` 与 `itcore_snapshot_epoch`、`prevAttemptText_.size()` 填 `SessionMemoryInputs`，返回 `sessionMemoryTotal`、`scrollback_bytes`、`history_limit_bytes`。`setHistoryMemoryLimit` 调 `itcore_set_history_limits(core_, 0, bytes)`，并把值记进 `appearance_.memoryLimitBytes`，之后的重连按它建核心。

## 4. 账本策略（`ui/include/uicfg/memory_ledger.h`，可移植）

```cpp
struct LedgerLimits {
  std::uint64_t session = 128ull << 20;
  std::uint64_t app = 512ull << 20;
  std::uint64_t newSessionEstimate = 16ull << 20;  // 新会话起步估算：网格 + 首批历史 + 归档余量
  std::uint64_t minHistory = 4ull << 20;           // 调低历史时的下限
};
struct SessionMemory { std::string paneId; std::uint64_t total, history, historyLimit; };
struct HistoryTrim { std::string paneId; std::uint64_t newLimit; };
struct LedgerDecision { std::uint64_t total = 0; std::vector<HistoryTrim> trims; };

LedgerDecision balanceMemory(const std::vector<SessionMemory>&, const LedgerLimits&);
bool admitNewSession(std::uint64_t currentTotal, const LedgerLimits&);
std::string memoryRefusedMessage(std::uint64_t currentTotal, const LedgerLimits&);
std::string historyTrimmedNote(const std::string& connectionName, std::uint64_t newLimit);
std::string memoryLine(std::uint64_t bytes);   // "12.3 MiB"，与区域设置无关
```

`balanceMemory` 规则（决定）：

1. **会话上限**：`total > session` 的会话，新历史上限 = `max(minHistory, history − (total − session))`；只在比现有上限小时产生 trim。
2. **应用上限**：按第 1 步之后的估计值计算合计；若 `> app`，按 `history` 从大到小（相同则按 paneId）依次把该会话的历史上限压到 `max(minHistory, history − 剩余超出)`，直到估计合计不超过 `app` 或已无可压。估计值 = 原 total − 被压掉的历史字节。
3. 每个会话至多一条 trim（取两步中更小的值）。输入顺序不影响结果。
4. 历史已低于 `minHistory` 的会话不再压；全部压到下限仍超出时，只返回已有的 trim（之后的新建会被第 5 条拒绝）。

`admitNewSession`：`currentTotal + newSessionEstimate <= app`。

`memoryRefusedMessage`：「内存不足：已用 430.5 MiB，上限 512 MiB。请关闭一些窗格后重试。」

`historyTrimmedNote`：「「web-1」的回滚历史已缩减到 37.0 MiB（内存上限）」。

## 5. 界面接线（`main.cpp`）

- 定时器（2 s，UI 线程）：收集每个有后端的窗格的 `memoryUsage()` → `balanceMemory` → 对每条 trim 调 `setHistoryMemoryLimit`，并在状态栏追加 `historyTrimmedNote`（同一窗格、同一新上限只提示一次）。
- 新建窗格的入口（`openTab`、`splitActive`、未连接占位上的「连接」）：先按最新一次计量的合计调用 `admitNewSession`；不允许就弹 `memoryRefusedMessage`（`MB_ICONWARNING`），不创建窗格 / 不启动会话。**重连不检查**（重连替换旧核心，不增加会话数）。首次启动的第一个本地窗格不检查。
- 诊断包（DS-15）：`DiagEnvironment` 增加一行「内存（账本）= 合计 X / 512 MiB，N 个会话；最大 Y」。只出数字，不出窗格名（窗格名可能含主机）。

## 6. 测试

平台无关，进 ctest：

- **核心计量**：新核心各项非零且 `total` 等于各项之和；输出大量行后 `scrollback_bytes` 增长；ED 3 / RIS 后回落；有待取事件时 `queue_bytes` > 0，取完回 0；开始 / 结束搜索时 `search_bytes` 变化。
- **`itcore_set_history_limits`**：调低后 `scrollback_bytes ≤ 新上限`、`history_limit_bytes` 等于新值、显示行数随之减少；字素池预算按新值变化（压缩阈值）；已取出的快照仍可读（ASan 下无悬空）。
- **快照**：触发字素池压缩前后，`itcore_snapshot_pool_bytes` 与 `pool_epoch` 的关系；`sessionMemoryTotal` 对同 epoch 不重复计、不同 epoch 计入旧 store。
- **账本策略**：单会话超限；应用超限从最大历史开始压；`minHistory` 下限；输入顺序无关；无超限时无 trim；`admitNewSession` 边界（恰好等于上限允许）；三段文案。
- **ABI-02**：新结构体的偏移与尺寸。
- **压力**（REVIEW 验收「100 次重连、快照滞留」）：在 `tests/app` 用真实核心模拟：10 个会话各输出到历史上限，跑 `balanceMemory` 并应用 trim，合计 ≤ 512 MiB 且每个会话 ≤ 128 MiB；同一核心 100 次「建核心 → 输出 → 取快照不放 → 压缩 → 放快照 → 销毁」，计量回到起点（ASan / TSan 预设下无泄漏、无悬空）。

只能在 Windows 上验的：

1. 开 8 个窗格各 `cat` 大文件到历史上限，任务管理器的进程内存与诊断包里的账本合计同一量级（账本不含显存与队列，会偏小）。
2. Profile 设 `memoryLimitMiB: 1024` 的窗格输出 200 MiB 后被压到约 128 MiB，状态栏提示一次。
3. 接近 512 MiB 时新开标签被拒绝、提示文字正确；关闭几个窗格后可以新开。
4. CI `mingw` 编译通过。
