## 本轮问题（2026-11-05 已修复）

- [x] **P1：Starting → Running 交接仍可能丢失关闭请求**
  - 位置：`platform/windows/conpty/conpty_transport.cpp:207–208,360–374`。
  - 性质：原有竞态仍未解决，并非本轮新增。
  - 可行交错：monitor 在线程退出事件发生后进入 `close(ProcessExited)`，读取到 `Starting`，随后被抢占；启动线程发布 `Running`，检查 `closeRequested_ == false` 后返回；monitor 恢复执行，按旧的 `Starting` 分支设置 `closeRequested_ = true` 后返回。此后没有线程再次消费该标志，也没有向 `closeRequest_` 发信号。
  - 影响：快速退出的子进程可能一直被报告为 Running，closer 留在等待中，自动清理和终态通知不发生；外部后续再次调用 close 才可能恢复。
  - 根因：原子的状态和请求标志并不使“读取状态 → 发布请求 → 启动方接管请求”成为原子事务；`closeReason_` 在这些路径也缺少统一同步。
  - 修复建议：用同一把生命周期锁保护状态转换、关闭请求及原因的发布和接管，或设计不会丢失请求的原子状态机；不要在持锁时执行回调、join 或阻塞清理。
  - 验收：用 barrier 确定性构造上述交错，验证无需第二次 close 就能进入终态；补充快速退出进程的 Windows 重复启动测试。
  - 证据：静态线程交错分析，尚未 Windows 实机复现。
  - 修复：新增生命周期锁 `lifeLock_`。`close()` 在锁内读状态并登记请求：Idle 直接收口，Starting 写 `closeRequested_` 和 `closeReason_`，Running / Closing 抢 `closeStarted_`。`start()` 的 Idle→Starting 也在锁内。新函数 `publishRunning()` 在锁内把状态设为 Running 并取走 `closeRequested_`，回调在锁外，三处发布 Running 都改用它。这样 close 要么看到 Running 自己发请求，要么请求被 `publishRunning` 取走。顺带收紧两点：closer 创建失败、`start` 同步收口期间，Starting 分支不再改写原因；`doClose` 在锁内读 `closeReason_`。持锁时不回调、不等待、不清理。
  - 未做：barrier 确定性测试。ConPTY 是 Win32 专属代码，本地无法编译和运行，仍待 Windows 故障注入。

- [x] **P2：新增 closeRequest_ 创建失败时会在启动中错误执行清理**
  - 位置：`platform/windows/conpty/conpty_transport.cpp:69,183,379–382`。
  - 性质：本轮新增事件的失败路径。
  - 触发条件：`CreateEventW` 创建 `closeRequest_` 返回空句柄，而后续 closer 线程成功创建。
  - 问题：构造函数不检查事件句柄；`closerMain()` 不检查 `WaitForSingleObject` 返回值。等待空句柄失败后，仍直接调用 `doClose()`。
  - 影响：closer 可在 start 尚未创建 / 发布 writer、monitor 句柄时关闭管道、进程并发出关闭完成信号；start 随后继续创建线程并发布 Running，破坏启动和关闭时序，可能访问已关闭句柄或发生数据竞争。
  - 修复建议：启动任何工作线程前验证全部同步事件创建成功；失败时通过明确的初始化失败路径释放已创建资源。等待结果必须为 `WAIT_OBJECT_0` 才允许执行正常关闭；异常等待不能被视为收到关闭请求。
  - 验收：单独注入 closeRequest_ 创建失败，确认不会启动子进程或工作线程，错误可见，销毁不阻塞；覆盖等待失败分支。
  - 证据：静态失败路径分析，尚未 Windows 故障注入复现。
  - 修复：构造函数逐个创建事件，记下第一个失败的错误码（`eventError_`）。`start()` 在建管道、线程、进程之前检查它，失败就走 `failStart(StartFailed, "CreateEvent", 错误码)`：状态为 Failed，错误可见；析构不阻塞，因为状态已是终态，`waitClosed` 对空句柄立即返回。`closerMain` 只有在等待结果为 `WAIT_OBJECT_0` 时才执行 `doClose`，其他结果记诊断 `closer-wait-failed` 后退出，不当成关闭请求。
