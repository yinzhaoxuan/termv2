# DS-18 第 3 版：设计复审意见

审查对象：[DS-18-字形运行渲染.md](DS-18-字形运行渲染.md)，2026-11-05 第 3 版。

**处理状态（2026-11-05）**：两条意见都已在 DS-18 第 4 版的设计中处理，对照表见 DS-18 §14。设计仍待批准，尚未实现。

以下仅记录当前仍需补齐的设计问题。上一轮的 RTL 判定来源、缓存分组输入、失败计划共享和计时口径已有针对性修订，不再重复列出。

- [x] **P1：统一字体并不能保证同一核心字素在一次塑形调用中完成（§4.2、§5.0–5.2）。**
  - §5.0 统一的是字体区间，但 §4.2 随后还要与 script 区间求交。只要 script 边界落在核心字素内部，同一个格仍会被拆成多个 `GetGlyphs / GetGlyphPlacements` 调用，即使它们使用同一个字体。
  - 因此 §5.0“跨塑形项累加只发生在不同格之间”和 §5.2“组合符的附着总在同一次 GetGlyphPlacements 里完成”目前没有成立的保证；§5.1 还保留了“同格分到两个回退字体项”的旧描述，与新规则不一致。
  - 当前核心 `Screen::join_cluster` 会把识别为 combining 的字符并入前一格，并不验证 script 一致。不能假设核心格边界天然包含所有 DirectWrite script 边界；跨 script 的组合序列、格式字符及其分析结果都需要覆盖。
  - 建议在 script/字体区间求交之后检查核心字素是否被拆开。对无法保证单次塑形的字素明确降级到旧逐格布局，或者给出可验证的 script 合并规则；不要只靠同字体下的自然 advance 累加来承诺附着正确。同步修正 §5.0–5.2 的不变量表述。
  - 验收：构造“一个核心格横跨两个 script 区间、字体相同”的纯函数输入，验证该格明确降级或按已定义规则合并，不会悄悄拆成两次塑形；Windows 再验证实际混合 script 组合序列的分析结果和画面。
  - **设计已处理**：DS-18 第 4 版 §5.0：改为不变量「每个不降级的核心格完整落在一个塑形项里」，由 `planItems` 保证：先按格统一字体，再与 script 求交并在 RTL 格边界切开，然后检查项边界是否落在格内部，落在内部的格降级（不做 script 合并），最后挖掉降级格。§5.1、§5.2 的表述已同步改正。单测覆盖「字体相同、格内跨两个 script」，并对所有输入断言这条不变量；跨 script 组合序列在 Windows 上记录分析结果和画面。

- [x] **P2：明确缓存中 legacyCells 的索引空间，并补齐定位接口的数据流（§5.0、§5.4、§8）。**
  - `legacyCells` 进入了与位置无关的 `ShapedRun` 缓存，但未说明其值是绝对列号、段内列偏移，还是不含尾格的核心格序号。这三者在段移动或宽字符出现时不等价。
  - 若缓存绝对列，挪列命中后会画错位置；若缓存段内列偏移，同文本/同格分组但格宽布局不同也可能错误。当前缓存键没有格宽，宜保存核心格序号或 UTF-16 字素范围，再在本次定位时映射到列。
  - `placeOnGrid` 当前只接收 `vector<ShapedItemView>`、`TextRun` 和列宽，而输出包含 `LegacyCell`。文档没有说明 `ShapedRun::legacyCells` 如何传入、或如何从缺失文本区间完整且无歧义地重建降级格。
  - 建议把降级索引固定为“段内核心格序号（不含尾格）”或 UTF-16 范围，并让定位接口显式接收整个 `ShapedRunView`（含降级信息）。定义 `LegacyCell` 从哪段文本取字、使用哪一格的宽度与裁剪，避免从字形缺口猜测。
  - 验收：同一缓存条目在不同绝对列复用；降级格前面有宽字尾格；相同文本/分组而宽度布局变化。所有情况下降级格与正常字形都应落在本次输入的正确列上，且每格只绘制一次。

  - **设计已处理**：DS-18 第 4 版 §4.1、§5.4、§8：`legacyCells` 固定为格序号（段内核心格编号，不含尾格）；`TextRun` 增加 `cellSpans` 和 `cellCols`；`placeOnGrid` 改为接收 `ShapedRunView`（含降级格），`LegacyCell` 片段的文字、列、宽度和裁剪都从本次输入算出；缓存值只含段内相对位置。单测覆盖跨列复用、前面有宽字尾格、同文本不同宽度布局三种情况，并断言每格只画一次。
