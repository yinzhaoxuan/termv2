# DS-18 第 2 版：设计复审意见

审查对象：[DS-18-字形运行渲染.md](DS-18-字形运行渲染.md)，2026-11-05 第 2 版。

**处理状态（2026-11-05）**：全部意见已在 DS-18 第 3 版的设计中处理，对照表见 DS-18 §13，每条下面注明对应章节。设计仍待批准，尚未实现。

以下仅列当前设计仍需处理的问题，不重复上一轮已经解决的意见。P1 为实现前需要解决的正确性问题；P2 为行为或验收契约需要补齐之处。

- [x] **P1：RTL 判定使用了不存在的 API 属性，并误用了 NO_VISUAL（§4.2）。**
  - `GetScriptProperties` 返回的 `DWRITE_SCRIPT_PROPERTIES` 没有 RTL 标志；`isCursiveWriting` 等字段也不能等价替代方向。`DWRITE_SCRIPT_SHAPES_NO_VISUAL` 表示不可见的控制/格式字符，不表示 RTL script。
  - 按当前描述无法实现可靠的 RTL 分支，还可能把格式控制字符误送入可见字形降级逻辑。
  - 建议明确可执行的方向判定来源，例如采用有版本和覆盖范围的 Unicode 方向/script 表，或只使用 `AnalyzeBidi` 的分析结果判定方向而不执行视觉重排。将 NO_VISUAL 独立处理，保留其不可见语义。
  - 验收增加阿拉伯文、希伯来文、非 RTL 的连写 script，以及方向控制字符；不能只列两个语言的名称作为全部判定规则。
  - 依据：[DWRITE_SCRIPT_PROPERTIES](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_1/ns-dwrite_1-dwrite_script_properties)、[DWRITE_SCRIPT_SHAPES](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/ne-dwrite-dwrite_script_shapes)。
  - **设计已处理**：DS-18 第 3 版 §4.2：方向改由 `AnalyzeBidi` 的解析层级判定，只读层级、不重排；奇数层级所在的格逐格塑形；`DWRITE_SCRIPT_PROPERTIES` 不再用于判断方向；`NO_VISUAL` 按不可见格式字符照常塑形；写明方向控制符的影响；手测补了希伯来文、蒙古文和方向控制符。

- [x] **P1：逐格塑形引入了缓存键没有表达的输入（§4.2、§8）。**
  - §4.2 要求 RTL 按“每个核心格”拆成塑形项，因此塑形项边界依赖 `colOfUnit` 的字素分组；§8 的键却只有拼接文本、格式、连字开关。
  - 相同 UTF-16 文本若具有不同的核心格边界，会命中同一缓存，却需要不同的逐格塑形调用和 `textBegin/textLength`。之后重新定位不能修正已经错误复用的塑形结果。设计当前也未建立“相同文本一定具有唯一核心格分组”的不变量。
  - 建议在需要逐格塑形的缓存键中包含相对 UTF-16 字素边界签名，或把这类内容按单个核心字素缓存；不必包含绝对列号。若选择依赖唯一分组不变量，应在接口上验证并证明它适用于快照编辑和所有调用方。
  - 验收：相同文本、不同字素分组不复用错误的塑形项；仅移动绝对列位置仍可命中。
  - **设计已处理**：DS-18 第 3 版 §8：缓存键加入核心格分组，即每格 UTF-16 长度的序列，与绝对列号无关；补了单测：相同文本、不同分组时不命中，只挪动列仍能命中。

- [x] **P2：跨字体项累加 advance 不保证组合符附着正确（§5.2、§10）。**
  - 定位单元解决了重复分配格宽，但两个字体项分别调用 `GetGlyphPlacements` 时，后一个项没有前一个字体的基字形，也没有跨字体的附着锚点。
  - 因此“基字符 advance + 组合符本项 offset”只能得到一个约定位置，不能保证组合符正确盖在基字符上；某些字体还可能为孤立组合符生成占位形。仅验证“下一格不受影响”会漏掉这个视觉错误。
  - 建议优先为整个核心字素寻找可用字体；仍必须跨字体时，明确采用旧逐格布局降级或接受有记录的视觉限制，不把自然位置累加等同于正确组合定位。增加真实字体下缺失组合符的 Windows 图像验证，纯函数测试只验证几何不串格。
  - 依据：[GetGlyphPlacements 的单字体面输入契约](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nf-dwrite-idwritetextanalyzer-getglyphplacements)。这是从该接口输入范围推导出的限制，不是已经实测的具体字体故障。
  - **设计已处理**：DS-18 第 3 版 §5.0：回退结果先按核心字素统一字体（`unifyGraphemeFonts`），找不到含全部码点的字体就按旧方式逐格绘制，同一字素不再跨字体项；纯函数只测几何，附着效果由 Windows 图像验证（§10 第 4 项）。

- [x] **P2：塑形失败后的块光标重画可能与底层走不同路径（§4.3、§7）。**
  - §4.3 规定一段失败后回退旧 DrawTextW；§7 又要求覆盖层查缓存或重新塑形，并宣称字体、位置、缩放完全一致。
  - 如果底层失败后回退，而覆盖层的重试成功，或二者采用不同失败处理，覆盖层就可能用不同的布局盖在底层上。当前设计没有将本帧隔离段的实际路径选择和结果交给覆盖层。
  - 建议本帧保留隔离段的绘制计划及降级标记；底层和反色覆盖层共用同一结果。若降级，两者一致走旧路径；如果两者重试，须规定同一帧的选择不能分叉。
  - 验收：对隔离段注入一次性塑形失败，验证底层与反色重画仍使用一致的布局，错误计数也不因覆盖层重复计入。
  - **设计已处理**：DS-18 第 3 版 §7：保存隔离段的绘制计划（共享的塑形结果、绘制片段和降级标记），覆盖层只换画刷，不查缓存、不重试；§8 的缓存值改为共享所有权；补了注入塑形失败的单测。

- [x] **P2：CPU 计时边界与“排除背景”的约定不一致（§9）。**
  - 当前渲染循环按行交错绘制背景、文本和装饰。直接从第一行文本前计时，到最后一行文本结束，会包含中间各行的背景调用，无法满足文档声称的“不含背景”，且可能使两条路径的计时口径不同。
  - 建议对每行/每段的文本工作分别计时并累加为帧样本，或明确拆分渲染阶段；须将文本转换、分段、分析、缓存查找、定位和 glyph 提交包含在内，并规定装饰矩形是否计入。两条路径采用同一口径，计时插桩不改变旧路径布局与缓存行为。
  - 验收：用可注入时钟构造背景、文本、装饰交错的样本，确认背景耗时不会进入文本样本；“全屏”分类以重画行覆盖范围判断，不能因为空白行没有字形就误判为部分重画。

  - **设计已处理**：DS-18 第 3 版 §9：在每段文本工作前后计时并累加，写明计入和不计入的内容，两条路径口径相同；分类按重画行数；用可注入时钟的单测验证交错绘制时背景不进入样本。
